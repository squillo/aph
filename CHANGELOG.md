# Changelog

All notable changes to APH (Agent per Human Notarization Protocol) will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0-draft] — 2026-05-21

### Added

- Initial public draft of the APH protocol specification.
- Canonical envelope shape (W3C Verifiable Credential 2.0).
- Two mandate types: `DelegationMandate` (ongoing) and `CommunicationMandate` (per-message).
- Five protocol roles: `HumanPrincipal`, `AgentSender`, `NotaryService`, `ChannelAdapter`, `RecipientEndpoint`.
- Two flow state machines: human-present (7 states) and human-not-present (5 states).
- A2A Agent Card extension descriptor (URI `aph://extensions/notarization/v1`).
- SD-JWT-VC profile pinning (draft-ietf-oauth-sd-jwt-vc-16, draft-ietf-oauth-selective-disclosure-jwt-22).
- 7 example envelope JSON files covering Slack, Email, Discord, Teams, WhatsApp, Google Chat, and iMessage channels.

### Added (revision 2026-05-21 — additive clarification within 0.1.0-draft)

- New §8.4 **Notary Key Material + Public-Key Discovery**. Defines the public/private keypair model for Notary Service operators and THREE publication mechanisms a verifier can use to resolve a notary's public key with NO prior trust relationship: (1) `did:key` self-describing decode, (2) `did:web` `.well-known/did.json` HTTPS resolution, (3) DNS TXT records at `_aph._notary.<domain>` (DKIM-style tag-list).
- §8.4.5 specifies the DNS TXT record name `_aph._notary.<domain>`, required tags (`v=APHv1`, `alg`, `k`), optional tags (`did`, `kid`, `notBefore`, `notAfter`), worked record examples, and verifier resolution flow.
- §8.4.6 defines verifier resolution order across mechanisms.
- §8.4.7 defines key rotation + overlap windows.
- §8.4.8 defines optional pinning + trust-on-first-use behavior for high-stakes verifiers.
- §13 IANA Considerations extended to reserve the underscore-prefixed DNS labels `_aph` and `_aph._notary` by convention (formal IANA registration deferred to v0.2).
- §14.1 normative references extended with `did:key`, `did:web`, RFC 1035, RFC 4034.
- §14.2 informative references extended with multicodec + multibase pointers.
- §8.3 step 2 cross-references §8.4 for resolution detail.

### Added (revision 2026-05-21b — driver's-license framing + revocation conceptual model within 0.1.0-draft)

- New §1.1 **Mental model — the agent's driver's license**. Frames APH credentials as drivers' licenses for agents, with the human as the issuing authority, the notary as the DMV, and bounded scope (channels, rate, time window, policy decision) directly analogous to license endorsements + restrictions + expiration. Establishes cross-jurisdiction portability (interstate-license framing) as a first-class property.
- New §1.1.1 **Concrete example** — two agents from different organizations negotiating a meeting across an A2A channel under APH, including notary-key resolution via `did:web` and DNS TXT (§8.4), revocation, and the recipient-side verification flow.
- §6.3 **Mandate lifecycle** rewritten. NEW §6.3.1 makes mandate revocation NORMATIVE in v0.1 at the conceptual layer (issuer-side `revoked` state, downstream issuance cutoff, recipient policy guidance, short-validity-window posture for v0.1). On-wire revocation transport (W3C Verifiable Credential Status List 2021 or equivalent) remains deferred to v0.2. NEW §6.3.2 makes expiration semantics explicit (no re-activation; new mandate required).
- §10.1 **A2A composition** expanded with explicit positioning ("A2A defines transport; APH defines the human authorization that rides on top") + back-reference to §1.1.1 worked example.
- §10.2 **AP2 composition** expanded with explicit positioning ("AP2 authorizes payment; APH authorizes the broader category of human-on-behalf-of actions, including the communication that surrounds a payment"). Adds the toll-booth / driver's-license / road-network framing of the A2A + AP2 + APH triad.
- §1 Abstract reworded to scope "outbound actions" more broadly than "outbound communications" — APH covers any human-authorized agent action, including messaging, scheduling, content authorship, and the communications surrounding payments.

### Added (revision 2026-08-13 — the principal signs; notary code attestation, within 0.1.0-draft)

APH is pre-production with no external adopters, so this correction lands **in place** rather than forking a version — there is one specification, `spec/aph-0.1.md`. Earlier drafts of §1.1/§3.1 promised that the human principal could sign directly while the wire format could not express it, which made every credential notary-attested in truth: a verifier learned that *a notary asserts* the human authorized an action, never that the human did.

- **§7.1.11 proof chains.** `proof` MAY be a single object or an array. As an array it is a W3C Verifiable Credentials 2.0 **proof chain** — a facility the data model already defines, not an APH invention — constrained to two roles: a principal proof carrying the authorization, then a notary countersignature covering the *complete* principal proof, so a notary cannot detach a principal's signature and re-attach it to a different envelope. Verifiers MUST verify in chain order.
- **§6.1 `DelegationMandate.principalSignature`** — the human's own signature over the standing grant, and the root of every credential issued under it. `notarySignature` now countersigns what the principal signed.
- **§7.1.7 `policy.attestationMode`** — closed enum, `PrincipalSigned` | `NotaryAttested`. **Absent means `NotaryAttested`**, so envelopes written before this revision remain valid and unambiguous. A verifier requiring `PrincipalSigned` MUST refuse `NotaryAttested` rather than silently accept the weaker claim, mirroring §8.4.6's no-downgrade rule for key discovery.
- **§7.1.7 `policy.delegationMandate` + new §7.1.7.1** — the complete parent mandate, embedded. In the human-not-present flow the human is asleep and cannot sign *this* message; `delegationMandateId` names their grant by **id only**, and an id is not verifiable. Embedding the mandate lets a recipient check the human's `principalSignature`, the granted scope, and the window entirely offline — closing the one hole that otherwise left the human's authorization asserted rather than proved.
- **New §7.2.1** — canonicalization base pinned per proof and per mandate signature, normatively, as the **empty string** rather than member removal. This settles the question earlier drafts left open, in the direction the reference implementation has always taken.
- **New §15 Notary Code Attestation** — a k-of-3 authority (any two of three holder keys) over content digests of published release artifacts, reusing Sigstore / in-toto / SLSA vocabulary rather than defining an APH schema. §15.7 states the limit **normatively**: an attestation proves what code was *published*, never what is *running*; any surface rendering an attestation badge MUST convey that, and a design implying otherwise is non-conformant.
- **§7.1.11 chain linkage.** Every proof in a chain carries an `id`; the notary proof carries `previousProof` naming the principal proof's `id`. Array position is a hint an intermediary can rearrange — the signed reference is the binding, and a verifier MUST reject a chain whose linkage is missing, dangling, or cyclic.
- **§7.3.1 worked `PrincipalSigned` example** — the same Slack reply as §7.3, with the mode declared, the parent mandate embedded, and the two-proof chain shown end to end.
- **§8.3.1** — amended verification: read the mode, resolve the principal key (free and offline for a `did:key` principal), verify the principal proof *before* the notary proof, and verify an embedded mandate when the envelope is notary-attested.

- **§7.2.1 issuance order is normative.** Each proof covers the document plus every proof *before* it and nothing after — W3C Data Integrity proof-chain semantics. So the notary **prepares** the complete envelope (including `notarization`), the principal signs *that*, and the notary countersigns. `decisionTimestamp <= principalProof.created <= notaryProof.created`. The principal's base carries its proof as a **one-element array**, which domain-separates it from a lone notary proof: a chain stripped of its countersignature therefore cannot be re-presented as a valid single-proof envelope. An earlier draft of this revision defined the principal's base as the whole envelope with every `proofValue` blanked, which is unconstructible: it would require the human to sign over the notary's proof object and decision timestamp, neither of which exists when the human signs.
- **§7.1.11 binds the label to the structure, both ways.** `attestationMode: PrincipalSigned` MUST accompany a two-element chain whose head verifies under a key resolving to `credentialSubject.humanPrincipal.id`; a chain MUST carry that label; a mismatch is rejected with `APH_E013`. Without this the mode is a self-asserted string — a notary key alone could write `PrincipalSigned` above a single notary proof whose `proofPurpose` is `assertionMethod`, indistinguishable by purpose from a principal proof.
- **§11 gains three error codes** (`APH_E011` principal signature invalid, `APH_E012` attestation mode refused, `APH_E013` proof chain invalid), so the closed taxonomy covers the rejections §8.3.1 now requires. `APH_E011` is deliberately distinct from `APH_E001` and `APH_E006`, which are both *notary* signatures: only `APH_E011` means the authorization itself is forged.
- **§15.5 defines how a verifier checks an attestation** — resolve all three authority keys through §8.4, fetch under the §8.4.4 transport rules, require two signatures from two *distinct* keys, bind the digest byte-for-byte, then apply local policy. §8.3.1 step 10 previously referenced a check the document never specified.
- **§7.1.9 declares `attestedDigest` and `attestationUri`**, which §15.3 lets a notary send. Parsing is strict, so a field a conformant notary may emit has to exist in the shape a conformant verifier parses.

- **§15.2 stops claiming reproducibility, and §15.6 names what blocks §15.** The subject of an attestation is a content digest of a *published release artifact*; the earlier wording said "reproducible build", which claims a determinism property APH does not require, does not test, and cannot deliver. The weaker property the digest does rest on is **publication closure** — the commit must be buildable from what is published alone. The consequence is now stated where a reader will look for it: an attestation says *these holders vouch that this digest is the release they published*, NOT *anyone can rebuild the source and derive this digest*. Without reproducibility a third party cannot re-derive it, so the mechanism binds the holders' word to an artifact rather than offering an independently checkable derivation. New **§15.6** lists the four preconditions that make §15 unimplementable today — the authority has no DID, the format is "one of three" (which is zero for an implementer), nothing is contracted to fetch an attestation document, and §11's closed taxonomy has no code for a failed check — and forbids advertising §15 support until all four are settled.

### Changed (revision 2026-08-13)

- **A Notary Service is now hostable by anyone.** It never holds the principal's key, so it cannot forge an authorization; its compromise costs availability and metadata, not credentials. The question about a notary becomes supply-chain (does it run published code) rather than custodial (is it trusted with a key) — which is what §15 exists to answer.
- **§3.1 prose reconciled** with the wire format, so the specification no longer promises a mode it cannot express.
- **§4, §5.2, §6.3, §8.2, §8.3, §8.4 and the security companion** were rewritten wherever they still taught the notary as the root signer — including §4's architecture diagram, which now shows the prepare / sign / countersign order, and `spec/security-considerations.md` §3.1, which previously said a leaked notary key lets an attacker "issue arbitrary envelopes under the human principal's name". It no longer can, except in the one shape where nothing the human signed is present: `NotaryAttested` with no embedded mandate. That residual risk is now stated where the claim used to be.
- **`spec/security-considerations.md` gains §2.6 attestation-mode downgrade**, the structural twin of §2.5's algorithm downgrade and strictly more consequential: `alg: none` costs a signature check, this costs the whole authorization claim.
- **`CONTRIBUTING.md` records the pre-production exception** that permits an in-place correction, and states when it expires — the first external adopter.

### Added (revision 2026-08-13, later the same day)

### Fixed (revision 2026-08-13)

- **§6.1's worked example omitted `principalSignature`**, which its own field table marks required. The example and the validation rules now carry it, with the principal check ordered before the countersignature.
- **The embedded mandate was never bound to the envelope carrying it.** §7.1.7.1 and §8.3.1 step 1d now require `humanPrincipalDid`, `agentDid` and `id` to match the envelope's own values; without those equalities any validly-signed mandate could be stapled to any envelope.
- **§7.1.7.1 states what "within scope" does not cover** (a mandate constrains channel, rate and time — not recipients, not content class), what embedding discloses (the human's entire standing grant, to every recipient), and that a verifier must bound work on unauthenticated input (RECOMMENDED 64 KiB) because canonicalization precedes signature verification.
- **§15.1 requires the two threshold signatures to come from two distinct holder keys** — otherwise one compromised holder signs twice and k-of-3 silently degrades to 1-of-3.
- Stale canonicalization language ("strip", "minus `proof.proofValue`") removed from §8.2 and §8.3, which contradicted §7.2.1 and would have failed every signature a conformant signer produced.

### Changed (revision 2026-08-13b — worked-example ids + wasm JSON-text boundary)

- **The worked examples no longer share envelope ids with the published channel examples.** §7.3's envelope id is now `…00f0` (was `…0001`, which `slack_reply_envelope.json` also carries) and §7.3.1's — and therefore the signed golden `principal_signed_envelope.json`'s — is now `…00f3` (was `…0002`, which `email_reply_envelope.json` also carries). ### Changed (revision 2026-08-14d — CI supply-chain hardening, doc truth, and §8.4.7 on `did:web`)

- **CI no longer pipes a remote installer into a shell.** The interpreter workflow installed wasm-pack with `curl … | sh`, which executes whatever that URL serves at the moment a job starts — unpinned, unverified, and different on every run by definition. It now installs `wasm-pack@0.15.0` through a commit-pinned installer action that verifies the published checksum, so the version CI runs is the version CI was reviewed with.
- **Both workflows declare top-level `permissions: contents: read`.** Neither needs a writable token — the crates.io upload is authorized by the registry token, not by the workflow token — so the grant is narrowed explicitly instead of inherited from repository defaults.
- **A manual dispatch can no longer publish.** The publish step fired on `startsWith(github.ref, 'refs/tags/') || (workflow_dispatch && !dry_run)`, while the tag-matches-crate-version guard beside it runs on tags ONLY. The second arm was therefore a real `cargo publish` from any ref with no version check whatsoever, contradicting the workflow header's own promise that dispatch is rehearsal-only. The dispatch arm is deleted: publication happens on an `aph-core-vX.Y.Z` tag and nowhere else. The dry-run rehearsal step is unchanged, and the `dry_run` input description now states the rehearsal-only truth.
- **Cargo build caching in the test job only.** The interpreter workflow warm-starts from a commit-pinned `rust-cache` scoped to the `interpreters/rust` workspace. The publish job deliberately gets none, and a comment there says why: an irreversible publish is rare and keeps a hermetic cold build rather than trusting restored state.
- **`skills/spec/SKILL.md` and `AGENTS.md` stop flattening a discovery failure into `APH_E008`.** Both taught that a published-and-broken mechanism "refuses on the spot with `APH_E008`". §8.4.6 requires the opposite: the refusal surfaces the FAILURE'S OWN code — `APH_E008` unreachable, `APH_E003` outside the validity window, `APH_E010` unsupported algorithm — while `APH_E014` remains terminal-absence-only. The SKILL error table already agreed with the spec; the prose beside it did not, and now does.
- **`skills/spec/SKILL.md` stops calling §15's subject a "reproducible build".** Its trust-model section described the notary code attestation as "k-of-3 authority over reproducible builds", the exact wording §15.2 was rewritten on 2026-08-13 to retract — that section now states in normative voice that the word it deliberately does not use is "reproducible", because nothing re-derives the digest. The skill says what §15.2 says: k-of-3 over content digests of published release artifacts, binding the holders' word to an artifact rather than offering an independently checkable derivation, alongside the §15.7 published-not-running limit it already carried.

The dated form remains the TXT mechanism's expression, no validity metadata is added to the document schema, and nothing is renumbered. ### Added (revision 2026-08-14e — `aph-resolver`: the adapters an adopter with no host can just link)

- **New crate `interpreters/rust/aph-resolver`** — ready-made implementations of `aph-core`'s two discovery ports: a §8.4.5 DNS TXT lookup over `hickory-resolver` and a §8.4.4 `did:web` document fetch over `reqwest`. Public surface is three items — `HickoryTxtLookup`, `ReqwestDocumentFetch`, and `resolve(did_url, at_rfc3339)`, which builds both and delegates to `composer::resolve` in the §8.4.6 order. It is in the workspace default members, so plain `cargo test` covers it; no CI edit was needed.
- **Who it is for, stated in the crate doc and enforced by the dependency graph.** It serves adopters with no adapter layer of their own — a CLI, a service, a test harness. A host that already owns a transport stack should implement the two ports over THAT stack instead and keep one place where outbound requests are made; two HTTP clients in one process means two timeout policies and two answers to "what did this machine connect to". **The dependency edges are confined to this crate**: `tokio`, `hickory-resolver`, `reqwest` and `futures-util` are linked by `aph-resolver` and by nothing else, so `aph-core`, `aph-conformance` and `aph-cli` gain no edge to a resolver, an HTTP client or an async runtime, and `cargo test -p aph-core` remains runnable with no network by construction.
- **Every parsing, selection and ordering rule stays in `aph-core`.** The new crate contributes I/O plus exactly one judgement, the absence/failure split, which only an adapter can see: NXDOMAIN — and NOERROR with no TXT records — is absence (`Ok(vec![])`, and the §8.4.6 sequence advances), while timeout, SERVFAIL and REFUSED are `APH_E008` and stop it. The split is a pure classifier over the resolver's response code, so it is tested with no network, and it fails closed on any error kind it does not recognise.
- **Security posture on the `did:web` fetch (five controls).** A deny table over EVERY resolved address before any connect — IPv4 loopback/this-network/RFC 1918/link-local/CGNAT/IETF-protocol/benchmark/TEST-NET/multicast/broadcast/reserved, the IPv6 equivalents, and the IPv4 addresses embedded in mapped, IPv4-compatible, NAT64 `64:ff9b::/96` and 6to4 forms re-checked through the v4 table — with the validated set then PINNED into the client so the connect cannot re-resolve; HTTPS only with no certificate-validation escape hatch; redirects refused plus an origin-equality re-check on the response; a 5 s connect and total budget with a 64 KiB body cap enforced WHILE streaming rather than after reading; and one bare `APH_E008` outward for every failure — no status, no address, no timing — so a verifier cannot be steered into acting as a network probe by whoever chose the DID.
- **Fixed — the `TxtRecordLookup` port doc listed NXDOMAIN as a transport failure.** Its `# Errors` section named "NXDOMAIN, timeout, SERVFAIL, refused" as `APH_E008` outcomes, contradicting the contract §8.4.6 depends on and the behaviour observed against real DNS: a notary that publishes only a DID Document has no `_aph._notary` name, so NXDOMAIN is the NORMAL answer on that path and the composer must advance. The doc now states NXDOMAIN and NOERROR-empty as ABSENCE (`Ok` with an empty `Vec`) and keeps timeout/SERVFAIL/REFUSED as the `APH_E008` list. Documentation only — no code in `aph-core` changed, and no error code moved.

### Added (revision 2026-08-15b — the revocation transport, within 0.1.0-draft)

APH is pre-production with no external adopters, so this lands **in place** in `spec/aph-0.1.md` rather than forking a version. The draft made revocation normative in §6.3.1 and then gave a recipient no way to observe one: the human could pull a Delegation Mandate, the notary would stop issuing against it, and a third party holding an envelope issued the hour before had no mechanism at all for learning that. The only mitigation on offer was "keep validity windows short" — which is advice about how long to be wrong for.

- **New §6.3.3 Revocation transport (normative)**, profiling **W3C Bitstring Status List v1.0**. Six sub-sections: the entry shape (§6.3.3.1), the derived endpoint and its same-origin binding (§6.3.3.2), the status list credential with its issuer binding and freshness bound (§6.3.3.3), the absent / unresolvable / revoked trichotomy (§6.3.3.4), the closed `statusPurpose` set (§6.3.3.5), and the string index with its reuse prohibition (§6.3.3.6).
- **The status endpoint's ORIGIN is derived from the notary's `did:web`, never read from the envelope.** It is computed from `credentialSubject.notarization.notaryService.id` under §8.4.4 step 2's rule, substituting `/.well-known/aph-status.json` for `/.well-known/did.json`. When an envelope carries `credentialStatus.statusListCredential`, that URL MUST be `https:` and same-origin with the derived endpoint; a cross-origin value is rejected **unfetched**. The attack this closes is the whole point of the section: if the envelope could name the host that answers "has this been revoked", then whoever holds a stale envelope also picks the host — and an attacker's host always answers *no*. Same-origin deliberately permits a different PATH, which is how a notary with more than one list points at the second while the origin stays derived.
- **New top-level `credentialStatus` field (§7.1.1 row), OMITTED when absent and never emitted as `null`** — unlike the neighbouring `linkedMandate`, whose bare-default serde form is why eight published examples carry an explicit null. An envelope offering no status reference is therefore byte-identical to a pre-revocation envelope, so all nine published examples, all seven golden fixtures, all seven inline conformance goldens and the four real Ed25519 signatures on `principal_signed_envelope.json` are untouched by this revision. It is declared as a core field rather than a §7.5 extension for the reason §7.1.9's attestation fields are: §7.1 parses strictly, so a field a notary may send must exist in the shape a verifier parses. §7.5's registry is also explicitly *vendor-originated*, and a W3C field has no vendor.
- **An APH profile of the W3C field, stated rather than assumed.** In VC 2.0 `credentialStatus` describes the credential carrying it; in APH it describes the **parent Delegation Mandate** named by `policy.delegationMandateId`, because §6.3.1 confines revocation to Delegation Mandates and leaves issued envelopes cryptographically valid. An envelope carrying `credentialStatus` MUST carry a non-null `delegationMandateId`, enforced at strict parse — a status reference with nothing to be the status of is malformed, not merely unhelpful.
- **§6.3.1 item 3 promoted MAY → MUST**, and §8.3 gains **step 8a**. A recipient that receives an envelope carrying a status reference MUST resolve it and MUST reject a revoked mandate. The old recipient-policy `MAY` sat in the subsection immediately above §6.3.2's verifier `MUST` for expiry: authority that ran out on schedule and authority a human deliberately pulled cannot carry opposite normative force. Step 8a is sub-numbered rather than renumbered because §8.3.1 references steps 9 and 10 by number, and it sits after the local checks because it is the only step that may cost a network round-trip.
- **§6.2's validation list gains revocation beside expiry.** The `delegationMandateId` bullet required the parent to exist, be unexpired, and allow the channel; it now also requires that the parent not be revoked at `issuedAt`.
- **The trichotomy is bind-when-present, fail-closed inside.** Absent ⇒ skip (enforcing a claim nobody made is not fail-closed, it is fail-arbitrary, and it would refuse every conformant pre-revision envelope). Present-and-unresolvable ⇒ REJECT with `APH_E008` — this is §8.4.6's *published and failed* rule one level up, and it exists so an attacker who can make the check **fail** cannot thereby choose that it is **skipped**. Revoked ⇒ REJECT with `APH_E015`. A verifier MAY additionally require a status reference; that is policy in the shape of §8.3.1 step 10, not protocol.
- **A normative freshness bound short enough to beat the mitigation it replaces.** A status list credential issued more than **5 minutes** ago MUST NOT be accepted (60s skew per §8.3 step 6); notaries republish at most every **2 minutes**; caches expire at or before the bound, RECOMMENDED 60s. The mitigation being replaced is a validity window RECOMMENDED at hours-to-days, so a bound measured in hours would cost a fetch and buy nothing. Five minutes is the interval the spec already treats as prompt (§6.2's default Communication Mandate expiry).
- **`statusPurpose` is a closed set of exactly one member, `"revocation"`.** `"suspension"` is excluded deliberately: suspension is reversible and §6.3.2 forbids re-activation, so a reversible purpose would describe a lifecycle APH does not have. An unrecognized purpose is a FAILURE at strict parse, never a skip — otherwise a producer disables the check on any verifier by writing a word that verifier has never seen.
- **`statusListIndex` is a STRING, and index reuse is PROHIBITED.** The string form is a correctness requirement, not a style choice: in runtimes where every JSON number is an IEEE-754 double, an index past 2^53 rounds silently and the verifier reads a *different bit* with no parse error — the same float-widening hazard that made the wasm boundary JSON text in both directions. Reuse is prohibited because the index rides inside the signed bytes of every envelope issued under a mandate, and those envelopes outlive it: reassigning an index re-points stored envelopes at an unrelated mandate, either refusing envelopes whose authority was never withdrawn or laundering ones issued under authority that was. Neither is detectable — the bytes are unchanged and the signature still verifies. An exhausted list is succeeded by a new list at a new path on the same origin, and the old one stays served.
- **§11 gains `APH_E015` `MandateRevoked` at last position (now fifteen codes)** — a withdrawn authorization over still-valid signatures, held distinct from `APH_E003`, which is authority that ran out on schedule. Reporting a revocation as a signature failure would send an operator to inspect key material when the answer is a human decision.
- **`APH_E008`'s meaning is widened, deliberately and in one place.** It now covers any protocol-mandated fetch from a notary-hosted surface — a DID Document under §8.4.4, a status list credential under §6.3.3 — rather than only a notarization request that timed out. Fetch, TLS, parse, proof, issuer, purpose and freshness failures on the status path all surface it, because the verifier's action and the operator's remedy are identical in every one; implementations SHOULD log which fired. The boundary with `APH_E014` is unchanged and restated: E014 is terminal ABSENCE of a *discovery* surface, which advances the §8.4.6 sequence, and there is no sequence to advance on the status path.
- **§14.1 pins the vintage normatively.** The draft cited "W3C Verifiable Credential Status List 2021 or equivalent" in three places and referenced no status standard at all in §14.1. `credentialStatus.type` is signed wire content under §7.1's strict parse and is the ONLY member that distinguishes the two vintages, so "or equivalent" would have produced two conformant-looking implementations that never interoperate. Bitstring Status List v1.0 is also the vintage whose terms the VC 2.0 context already defines, so `@context` is unchanged and no `w3id.org/aph/v1` term is claimed.
- **`spec/security-considerations.md` gains §6.1** — the privacy analysis this transport owes. Checking status is a **phone-home**: every prior step in §8.3 is offline or resolves hour-cacheable key material, while step 8a opens a TLS connection to the issuing notary at the moment of verification, so the notary learns who is verifying and when — a disclosure APH did not previously make. A bitstring list gives herd privacy (the whole list is fetched, so the fetch does not name the mandate), the derived origin means a recipient cannot be steered into probing a host of the sender's choosing, and the short freshness bound cuts the other way by limiting how much caching can hide. Mitigations named: scheduled rather than on-demand fetching, a shared egress or caching proxy, and the residual-risk option, which stays conformant only for envelopes carrying no status reference. §3.1 and §7 also record the limit that matters against a *compromised notary key*: a list that key signs is worth nothing against its holder, so key compromise is still answered by rotation (§8.4.7).
- **The four deferral sites that would have left the document self-contradicting are all rewritten**: §1.1's driver's-license bullet, §1.1.1's worked example (Bob's agent now refuses with `APH_E015`), §3.2's Non-Goals entry (which was an entire bullet titled "A revocation **transport**" and is now the narrower non-goal that survives — no general credential-status service, no status for envelopes or Communication Mandates, no suspension), and Appendix B's Future Work bullet. §12's summary of recipient obligations gains the new MUST.
- **`aph-core` implements the code, and a pre-existing hole in its own closed-set tripwire is repaired.** `AphError::MandateRevoked` lands with its `code()`, `suggestion()` and `mandate_revoked()` constructor. The test module's `all_variants()` had omitted `NotaryKeyNotPublished` since the day `APH_E014` landed — so the count assert read thirteen against a §11 that said fourteen, and E014 was swept by NONE of the three all-variants tests (code format, non-empty suggestion, Display carries the code). Both missing entries are restored, the assert reads fifteen, and the test is renamed accordingly: a sweep is only worth its comment if the list it walks is the whole enum.
- **Documentation swept for the count and the new code**: `AGENTS.md` invariant 4 (fourteen → fifteen, plus the E015 and widened-E008 clauses), `skills/spec/SKILL.md` (frontmatter range, table heading, the new row, the widened E008 row, the wire-shape table's `credentialStatus` entry, and the §6.1 mandate bullet, which still taught "transport deferred to v0.2"), `commands/conformance.md`'s error range, and `interpreters/rust/aph-core/README.md`, whose taxonomy line still read `APH_E001`–`APH_E010` and was stale by five. §15.6 precondition 4 said §11 was "a closed taxonomy of thirteen" while §11 itself said fourteen — a same-document off-by-one, now correct at fifteen. The SKILL repo map claimed "8 golden envelope JSON files … All 8 are `NotaryAttested`"; nine exist and one is `PrincipalSigned` with four real signatures.
