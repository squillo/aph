# Changelog

All notable changes to APH (Agent per Human Notarization Protocol) will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0-draft] — 2026-05-21

### Added

- Initial public draft of the APH protocol specification.
- Canonical envelope shape (W3C Verifiable Credential 2.0).
- Two mandate types: `DelegationMandate` (ongoing) and `CommunicationMandate` (per-message).
- Five protocol roles: `HumanPrincipal`, `AgentSender`, `NotaryService`, `ChannelAdapter`, `RecipientEndpoint`.
- Two flow state machines: human-present (7 states) and human-not-present (5 states).
- A2A Agent Card extension descriptor (URI `aph://extensions/notarization/v1`).
- SD-JWT-VC profile pinning (draft-ietf-oauth-sd-jwt-vc-16, draft-ietf-oauth-selective-disclosure-jwt-22).
- 7 example envelope JSON files covering Slack, Email, Discord, Teams, WhatsApp, Google Chat, and iMessage channels.

### Added (revision 2026-05-21 — additive clarification within 0.1.0-draft)

- New §8.4 **Notary Key Material + Public-Key Discovery**. Defines the public/private keypair model for Notary Service operators and THREE publication mechanisms a verifier can use to resolve a notary's public key with NO prior trust relationship: (1) `did:key` self-describing decode, (2) `did:web` `.well-known/did.json` HTTPS resolution, (3) DNS TXT records at `_aph._notary.<domain>` (DKIM-style tag-list).
- §8.4.5 specifies the DNS TXT record name `_aph._notary.<domain>`, required tags (`v=APHv1`, `alg`, `k`), optional tags (`did`, `kid`, `notBefore`, `notAfter`), worked record examples, and verifier resolution flow.
- §8.4.6 defines verifier resolution order across mechanisms.
- §8.4.7 defines key rotation + overlap windows.
- §8.4.8 defines optional pinning + trust-on-first-use behavior for high-stakes verifiers.
- §13 IANA Considerations extended to reserve the underscore-prefixed DNS labels `_aph` and `_aph._notary` by convention (formal IANA registration deferred to v0.2).
- §14.1 normative references extended with `did:key`, `did:web`, RFC 1035, RFC 4034.
- §14.2 informative references extended with multicodec + multibase pointers.
- §8.3 step 2 cross-references §8.4 for resolution detail.

### Added (revision 2026-05-21b — driver's-license framing + revocation conceptual model within 0.1.0-draft)

- New §1.1 **Mental model — the agent's driver's license**. Frames APH credentials as drivers' licenses for agents, with the human as the issuing authority, the notary as the DMV, and bounded scope (channels, rate, time window, policy decision) directly analogous to license endorsements + restrictions + expiration. Establishes cross-jurisdiction portability (interstate-license framing) as a first-class property.
- New §1.1.1 **Concrete example** — two agents from different organizations negotiating a meeting across an A2A channel under APH, including notary-key resolution via `did:web` and DNS TXT (§8.4), revocation, and the recipient-side verification flow.
- §6.3 **Mandate lifecycle** rewritten. NEW §6.3.1 makes mandate revocation NORMATIVE in v0.1 at the conceptual layer (issuer-side `revoked` state, downstream issuance cutoff, recipient policy guidance, short-validity-window posture for v0.1). On-wire revocation transport (W3C Verifiable Credential Status List 2021 or equivalent) remains deferred to v0.2. NEW §6.3.2 makes expiration semantics explicit (no re-activation; new mandate required).
- §10.1 **A2A composition** expanded with explicit positioning ("A2A defines transport; APH defines the human authorization that rides on top") + back-reference to §1.1.1 worked example.
- §10.2 **AP2 composition** expanded with explicit positioning ("AP2 authorizes payment; APH authorizes the broader category of human-on-behalf-of actions, including the communication that surrounds a payment"). Adds the toll-booth / driver's-license / road-network framing of the A2A + AP2 + APH triad.
- §1 Abstract reworded to scope "outbound actions" more broadly than "outbound communications" — APH covers any human-authorized agent action, including messaging, scheduling, content authorship, and the communications surrounding payments.

### Added (revision 2026-08-13 — the principal signs; notary code attestation, within 0.1.0-draft)

APH is pre-production with no external adopters, so this correction lands **in place** rather than forking a version — there is one specification, `spec/aph-0.1.md`. Earlier drafts of §1.1/§3.1 promised that the human principal could sign directly while the wire format could not express it, which made every credential notary-attested in truth: a verifier learned that *a notary asserts* the human authorized an action, never that the human did.

- **§7.1.11 proof chains.** `proof` MAY be a single object or an array. As an array it is a W3C Verifiable Credentials 2.0 **proof chain** — a facility the data model already defines, not an APH invention — constrained to two roles: a principal proof carrying the authorization, then a notary countersignature covering the *complete* principal proof, so a notary cannot detach a principal's signature and re-attach it to a different envelope. Verifiers MUST verify in chain order.
- **§6.1 `DelegationMandate.principalSignature`** — the human's own signature over the standing grant, and the root of every credential issued under it. `notarySignature` now countersigns what the principal signed.
- **§7.1.7 `policy.attestationMode`** — closed enum, `PrincipalSigned` | `NotaryAttested`. **Absent means `NotaryAttested`**, so envelopes written before this revision remain valid and unambiguous. A verifier requiring `PrincipalSigned` MUST refuse `NotaryAttested` rather than silently accept the weaker claim, mirroring §8.4.6's no-downgrade rule for key discovery.
- **§7.1.7 `policy.delegationMandate` + new §7.1.7.1** — the complete parent mandate, embedded. In the human-not-present flow the human is asleep and cannot sign *this* message; `delegationMandateId` names their grant by **id only**, and an id is not verifiable. Embedding the mandate lets a recipient check the human's `principalSignature`, the granted scope, and the window entirely offline — closing the one hole that otherwise left the human's authorization asserted rather than proved.
- **New §7.2.1** — canonicalization base pinned per proof and per mandate signature, normatively, as the **empty string** rather than member removal. This settles the question earlier drafts left open, in the direction the reference implementation has always taken.
- **New §15 Notary Code Attestation** — a k-of-3 authority (any two of three holder keys) over content digests of published release artifacts, reusing Sigstore / in-toto / SLSA vocabulary rather than defining an APH schema. §15.7 states the limit **normatively**: an attestation proves what code was *published*, never what is *running*; any surface rendering an attestation badge MUST convey that, and a design implying otherwise is non-conformant.
- **§7.1.11 chain linkage.** Every proof in a chain carries an `id`; the notary proof carries `previousProof` naming the principal proof's `id`. Array position is a hint an intermediary can rearrange — the signed reference is the binding, and a verifier MUST reject a chain whose linkage is missing, dangling, or cyclic.
- **§7.3.1 worked `PrincipalSigned` example** — the same Slack reply as §7.3, with the mode declared, the parent mandate embedded, and the two-proof chain shown end to end.
- **§8.3.1** — amended verification: read the mode, resolve the principal key (free and offline for a `did:key` principal), verify the principal proof *before* the notary proof, and verify an embedded mandate when the envelope is notary-attested.

- **§7.2.1 issuance order is normative.** Each proof covers the document plus every proof *before* it and nothing after — W3C Data Integrity proof-chain semantics. So the notary **prepares** the complete envelope (including `notarization`), the principal signs *that*, and the notary countersigns. `decisionTimestamp <= principalProof.created <= notaryProof.created`. The principal's base carries its proof as a **one-element array**, which domain-separates it from a lone notary proof: a chain stripped of its countersignature therefore cannot be re-presented as a valid single-proof envelope. An earlier draft of this revision defined the principal's base as the whole envelope with every `proofValue` blanked, which is unconstructible: it would require the human to sign over the notary's proof object and decision timestamp, neither of which exists when the human signs.
- **§7.1.11 binds the label to the structure, both ways.** `attestationMode: PrincipalSigned` MUST accompany a two-element chain whose head verifies under a key resolving to `credentialSubject.humanPrincipal.id`; a chain MUST carry that label; a mismatch is rejected with `APH_E013`. Without this the mode is a self-asserted string — a notary key alone could write `PrincipalSigned` above a single notary proof whose `proofPurpose` is `assertionMethod`, indistinguishable by purpose from a principal proof.
- **§11 gains three error codes** (`APH_E011` principal signature invalid, `APH_E012` attestation mode refused, `APH_E013` proof chain invalid), so the closed taxonomy covers the rejections §8.3.1 now requires. `APH_E011` is deliberately distinct from `APH_E001` and `APH_E006`, which are both *notary* signatures: only `APH_E011` means the authorization itself is forged.
- **§15.5 defines how a verifier checks an attestation** — resolve all three authority keys through §8.4, fetch under the §8.4.4 transport rules, require two signatures from two *distinct* keys, bind the digest byte-for-byte, then apply local policy. §8.3.1 step 10 previously referenced a check the document never specified.
- **§7.1.9 declares `attestedDigest` and `attestationUri`**, which §15.3 lets a notary send. Parsing is strict, so a field a conformant notary may emit has to exist in the shape a conformant verifier parses.

- **§15.2 stops claiming reproducibility, and §15.6 names what blocks §15.** The subject of an attestation is a content digest of a *published release artifact*; the earlier wording said "reproducible build", which claims a determinism property APH does not require, does not test, and cannot deliver. The weaker property the digest does rest on is **publication closure** — the commit must be buildable from what is published alone. The consequence is now stated where a reader will look for it: an attestation says *these holders vouch that this digest is the release they published*, NOT *anyone can rebuild the source and derive this digest*. Without reproducibility a third party cannot re-derive it, so the mechanism binds the holders' word to an artifact rather than offering an independently checkable derivation. New **§15.6** lists the four preconditions that make §15 unimplementable today — the authority has no DID, the format is "one of three" (which is zero for an implementer), nothing is contracted to fetch an attestation document, and §11's closed taxonomy has no code for a failed check — and forbids advertising §15 support until all four are settled.

### Changed (revision 2026-08-13)

- **A Notary Service is now hostable by anyone.** It never holds the principal's key, so it cannot forge an authorization; its compromise costs availability and metadata, not credentials. The question about a notary becomes supply-chain (does it run published code) rather than custodial (is it trusted with a key) — which is what §15 exists to answer.
- **§3.1 prose reconciled** with the wire format, so the specification no longer promises a mode it cannot express.
- **§4, §5.2, §6.3, §8.2, §8.3, §8.4 and the security companion** were rewritten wherever they still taught the notary as the root signer — including §4's architecture diagram, which now shows the prepare / sign / countersign order, and `spec/security-considerations.md` §3.1, which previously said a leaked notary key lets an attacker "issue arbitrary envelopes under the human principal's name". It no longer can, except in the one shape where nothing the human signed is present: `NotaryAttested` with no embedded mandate. That residual risk is now stated where the claim used to be.
- **`spec/security-considerations.md` gains §2.6 attestation-mode downgrade**, the structural twin of §2.5's algorithm downgrade and strictly more consequential: `alg: none` costs a signature check, this costs the whole authorization claim.
- **`CONTRIBUTING.md` records the pre-production exception** that permits an in-place correction, and states when it expires — the first external adopter.

### Fixed (revision 2026-08-13)

- **§6.1's worked example omitted `principalSignature`**, which its own field table marks required. The example and the validation rules now carry it, with the principal check ordered before the countersignature.
- **The embedded mandate was never bound to the envelope carrying it.** §7.1.7.1 and §8.3.1 step 1d now require `humanPrincipalDid`, `agentDid` and `id` to match the envelope's own values; without those equalities any validly-signed mandate could be stapled to any envelope.
- **§7.1.7.1 states what "within scope" does not cover** (a mandate constrains channel, rate and time — not recipients, not content class), what embedding discloses (the human's entire standing grant, to every recipient), and that a verifier must bound work on unauthenticated input (RECOMMENDED 64 KiB) because canonicalization precedes signature verification.
- **§15.1 requires the two threshold signatures to come from two distinct holder keys** — otherwise one compromised holder signs twice and k-of-3 silently degrades to 1-of-3.
- Stale canonicalization language ("strip", "minus `proof.proofValue`") removed from §8.2 and §8.3, which contradicted §7.2.1 and would have failed every signature a conformant signer produced.

### Changed (revision 2026-08-13b — worked-example ids + wasm JSON-text boundary)

### Changed (revision 2026-08-14d — CI supply-chain hardening, doc truth, and §8.4.7 on `did:web`)

- **CI no longer pipes a remote installer into a shell.** The interpreter workflow installed wasm-pack with `curl … | sh`, which executes whatever that URL serves at the moment a job starts — unpinned, unverified, and different on every run by definition. It now installs `wasm-pack@0.15.0` through a commit-pinned installer action that verifies the published checksum, so the version CI runs is the version CI was reviewed with.
- **Both workflows declare top-level `permissions: contents: read`.** Neither needs a writable token — the crates.io upload is authorized by the registry token, not by the workflow token — so the grant is narrowed explicitly instead of inherited from repository defaults.
- **A manual dispatch can no longer publish.** The publish step fired on `startsWith(github.ref, 'refs/tags/') || (workflow_dispatch && !dry_run)`, while the tag-matches-crate-version guard beside it runs on tags ONLY. The second arm was therefore a real `cargo publish` from any ref with no version check whatsoever, contradicting the workflow header's own promise that dispatch is rehearsal-only. The dispatch arm is deleted: publication happens on an `aph-core-vX.Y.Z` tag and nowhere else. The dry-run rehearsal step is unchanged, and the `dry_run` input description now states the rehearsal-only truth.
- **Cargo build caching in the test job only.** The interpreter workflow warm-starts from a commit-pinned `rust-cache` scoped to the `interpreters/rust` workspace. The publish job deliberately gets none, and a comment there says why: an irreversible publish is rare and keeps a hermetic cold build rather than trusting restored state.
- **`skills/spec/SKILL.md` and `AGENTS.md` stop flattening a discovery failure into `APH_E008`.** Both taught that a published-and-broken mechanism "refuses on the spot with `APH_E008`". §8.4.6 requires the opposite: the refusal surfaces the FAILURE'S OWN code — `APH_E008` unreachable, `APH_E003` outside the validity window, `APH_E010` unsupported algorithm — while `APH_E014` remains terminal-absence-only. The SKILL error table already agreed with the spec; the prose beside it did not, and now does.
- **`skills/spec/SKILL.md` stops calling §15's subject a "reproducible build".** Its trust-model section described the notary code attestation as "k-of-3 authority over reproducible builds", the exact wording §15.2 was rewritten on 2026-08-13 to retract — that section now states in normative voice that the word it deliberately does not use is "reproducible", because nothing re-derives the digest. The skill says what §15.2 says: k-of-3 over content digests of published release artifacts, binding the holders' word to an artifact rather than offering an independently checkable derivation, alongside the §15.7 published-not-running limit it already carried.

### Added (revision 2026-08-14e — `aph-resolver`: the adapters an adopter with no host can just link)

- **Fixed — the `TxtRecordLookup` port doc listed NXDOMAIN as a transport failure.** Its `# Errors` section named "NXDOMAIN, timeout, SERVFAIL, refused" as `APH_E008` outcomes, contradicting the contract §8.4.6 depends on and the behaviour observed against real DNS: a notary that publishes only a DID Document has no `_aph._notary` name, so NXDOMAIN is the NORMAL answer on that path and the composer must advance. The doc now states NXDOMAIN and NOERROR-empty as ABSENCE (`Ok` with an empty `Vec`) and keeps timeout/SERVFAIL/REFUSED as the `APH_E008` list. Documentation only — no code in `aph-core` changed, and no error code moved.

### Added (revision 2026-08-15b — the revocation transport, within 0.1.0-draft)

APH is pre-production with no external adopters, so this lands **in place** in `spec/aph-0.1.md` rather than forking a version. The draft made revocation normative in §6.3.1 and then gave a recipient no way to observe one: the human could pull a Delegation Mandate, the notary would stop issuing against it, and a third party holding an envelope issued the hour before had no mechanism at all for learning that. The only mitigation on offer was "keep validity windows short" — which is advice about how long to be wrong for.

- **New §6.3.3 Revocation transport (normative)**, profiling **W3C Bitstring Status List v1.0**. Six sub-sections: the entry shape (§6.3.3.1), the derived endpoint and its same-origin binding (§6.3.3.2), the status list credential with its issuer binding and freshness bound (§6.3.3.3), the absent / unresolvable / revoked trichotomy (§6.3.3.4), the closed `statusPurpose` set (§6.3.3.5), and the string index with its reuse prohibition (§6.3.3.6).
- **The status endpoint's ORIGIN is derived from the notary's `did:web`, never read from the envelope.** It is computed from `credentialSubject.notarization.notaryService.id` under §8.4.4 step 2's rule, substituting `/.well-known/aph-status.json` for `/.well-known/did.json`. When an envelope carries `credentialStatus.statusListCredential`, that URL MUST be `https:` and same-origin with the derived endpoint; a cross-origin value is rejected **unfetched**. The attack this closes is the whole point of the section: if the envelope could name the host that answers "has this been revoked", then whoever holds a stale envelope also picks the host — and an attacker's host always answers *no*. Same-origin deliberately permits a different PATH, which is how a notary with more than one list points at the second while the origin stays derived.
- **New top-level `credentialStatus` field (§7.1.1 row), OMITTED when absent and never emitted as `null`** — unlike the neighbouring `linkedMandate`, whose bare-default serde form is why eight published examples carry an explicit null. An envelope offering no status reference is therefore byte-identical to a pre-revocation envelope, so all nine published examples, all seven golden fixtures, all seven inline conformance goldens and the four real Ed25519 signatures on `principal_signed_envelope.json` are untouched by this revision. It is declared as a core field rather than a §7.5 extension for the reason §7.1.9's attestation fields are: §7.1 parses strictly, so a field a notary may send must exist in the shape a verifier parses. §7.5's registry is also explicitly *vendor-originated*, and a W3C field has no vendor.
- **An APH profile of the W3C field, stated rather than assumed.** In VC 2.0 `credentialStatus` describes the credential carrying it; in APH it describes the **parent Delegation Mandate** named by `policy.delegationMandateId`, because §6.3.1 confines revocation to Delegation Mandates and leaves issued envelopes cryptographically valid. An envelope carrying `credentialStatus` MUST carry a non-null `delegationMandateId`, enforced at strict parse — a status reference with nothing to be the status of is malformed, not merely unhelpful.
- **§6.3.1 item 3 promoted MAY → MUST**, and §8.3 gains **step 8a**. A recipient that receives an envelope carrying a status reference MUST resolve it and MUST reject a revoked mandate. The old recipient-policy `MAY` sat in the subsection immediately above §6.3.2's verifier `MUST` for expiry: authority that ran out on schedule and authority a human deliberately pulled cannot carry opposite normative force. Step 8a is sub-numbered rather than renumbered because §8.3.1 references steps 9 and 10 by number, and it sits after the local checks because it is the only step that may cost a network round-trip.
- **§6.2's validation list gains revocation beside expiry.** The `delegationMandateId` bullet required the parent to exist, be unexpired, and allow the channel; it now also requires that the parent not be revoked at `issuedAt`.
- **The trichotomy is bind-when-present, fail-closed inside.** Absent ⇒ skip (enforcing a claim nobody made is not fail-closed, it is fail-arbitrary, and it would refuse every conformant pre-revision envelope). Present-and-unresolvable ⇒ REJECT with `APH_E008` — this is §8.4.6's *published and failed* rule one level up, and it exists so an attacker who can make the check **fail** cannot thereby choose that it is **skipped**. Revoked ⇒ REJECT with `APH_E015`. A verifier MAY additionally require a status reference; that is policy in the shape of §8.3.1 step 10, not protocol.
- **A normative freshness bound short enough to beat the mitigation it replaces.** A status list credential issued more than **5 minutes** ago MUST NOT be accepted (60s skew per §8.3 step 6); notaries republish at most every **2 minutes**; caches expire at or before the bound, RECOMMENDED 60s. The mitigation being replaced is a validity window RECOMMENDED at hours-to-days, so a bound measured in hours would cost a fetch and buy nothing. Five minutes is the interval the spec already treats as prompt (§6.2's default Communication Mandate expiry).
- **`statusPurpose` is a closed set of exactly one member, `"revocation"`.** `"suspension"` is excluded deliberately: suspension is reversible and §6.3.2 forbids re-activation, so a reversible purpose would describe a lifecycle APH does not have. An unrecognized purpose is a FAILURE at strict parse, never a skip — otherwise a producer disables the check on any verifier by writing a word that verifier has never seen.
- **`statusListIndex` is a STRING, and index reuse is PROHIBITED.** The string form is a correctness requirement, not a style choice: in runtimes where every JSON number is an IEEE-754 double, an index past 2^53 rounds silently and the verifier reads a *different bit* with no parse error — the same float-widening hazard that made the wasm boundary JSON text in both directions. Reuse is prohibited because the index rides inside the signed bytes of every envelope issued under a mandate, and those envelopes outlive it: reassigning an index re-points stored envelopes at an unrelated mandate, either refusing envelopes whose authority was never withdrawn or laundering ones issued under authority that was. Neither is detectable — the bytes are unchanged and the signature still verifies. An exhausted list is succeeded by a new list at a new path on the same origin, and the old one stays served.
- **§11 gains `APH_E015` `MandateRevoked` at last position (now fifteen codes)** — a withdrawn authorization over still-valid signatures, held distinct from `APH_E003`, which is authority that ran out on schedule. Reporting a revocation as a signature failure would send an operator to inspect key material when the answer is a human decision.
- **`APH_E008`'s meaning is widened, deliberately and in one place.** It now covers any protocol-mandated fetch from a notary-hosted surface — a DID Document under §8.4.4, a status list credential under §6.3.3 — rather than only a notarization request that timed out. Fetch, TLS, parse, proof, issuer, purpose and freshness failures on the status path all surface it, because the verifier's action and the operator's remedy are identical in every one; implementations SHOULD log which fired. The boundary with `APH_E014` is unchanged and restated: E014 is terminal ABSENCE of a *discovery* surface, which advances the §8.4.6 sequence, and there is no sequence to advance on the status path.
- **§14.1 pins the vintage normatively.** The draft cited "W3C Verifiable Credential Status List 2021 or equivalent" in three places and referenced no status standard at all in §14.1. `credentialStatus.type` is signed wire content under §7.1's strict parse and is the ONLY member that distinguishes the two vintages, so "or equivalent" would have produced two conformant-looking implementations that never interoperate. Bitstring Status List v1.0 is also the vintage whose terms the VC 2.0 context already defines, so `@context` is unchanged and no `w3id.org/aph/v1` term is claimed.
- **`spec/security-considerations.md` gains §6.1** — the privacy analysis this transport owes. Checking status is a **phone-home**: every prior step in §8.3 is offline or resolves hour-cacheable key material, while step 8a opens a TLS connection to the issuing notary at the moment of verification, so the notary learns who is verifying and when — a disclosure APH did not previously make. A bitstring list gives herd privacy (the whole list is fetched, so the fetch does not name the mandate), the derived origin means a recipient cannot be steered into probing a host of the sender's choosing, and the short freshness bound cuts the other way by limiting how much caching can hide. Mitigations named: scheduled rather than on-demand fetching, a shared egress or caching proxy, and the residual-risk option, which stays conformant only for envelopes carrying no status reference. §3.1 and §7 also record the limit that matters against a *compromised notary key*: a list that key signs is worth nothing against its holder, so key compromise is still answered by rotation (§8.4.7).
- **The four deferral sites that would have left the document self-contradicting are all rewritten**: §1.1's driver's-license bullet, §1.1.1's worked example (Bob's agent now refuses with `APH_E015`), §3.2's Non-Goals entry (which was an entire bullet titled "A revocation **transport**" and is now the narrower non-goal that survives — no general credential-status service, no status for envelopes or Communication Mandates, no suspension), and Appendix B's Future Work bullet. §12's summary of recipient obligations gains the new MUST.
- **`aph-core` implements the code, and a pre-existing hole in its own closed-set tripwire is repaired.** `AphError::MandateRevoked` lands with its `code()`, `suggestion()` and `mandate_revoked()` constructor. The test module's `all_variants()` had omitted `NotaryKeyNotPublished` since the day `APH_E014` landed — so the count assert read thirteen against a §11 that said fourteen, and E014 was swept by NONE of the three all-variants tests (code format, non-empty suggestion, Display carries the code). Both missing entries are restored, the assert reads fifteen, and the test is renamed accordingly: a sweep is only worth its comment if the list it walks is the whole enum.
- **Documentation swept for the count and the new code**: `AGENTS.md` invariant 4 (fourteen → fifteen, plus the E015 and widened-E008 clauses), `skills/spec/SKILL.md` (frontmatter range, table heading, the new row, the widened E008 row, the wire-shape table's `credentialStatus` entry, and the §6.1 mandate bullet, which still taught "transport deferred to v0.2"), `commands/conformance.md`'s error range, and `interpreters/rust/aph-core/README.md`, whose taxonomy line still read `APH_E001`–`APH_E010` and was stale by five. §15.6 precondition 4 said §11 was "a closed taxonomy of thirteen" while §11 itself said fourteen — a same-document off-by-one, now correct at fifteen. The SKILL repo map claimed "8 golden envelope JSON files … All 8 are `NotaryAttested`"; nine exist and one is `PrincipalSigned` with four real signatures.

### Changed (revision 2026-08-16 — absence becomes a type; **BREAKING** for `aph-core` 0.1.0-alpha.1 port implementors)

**An empty collection is not a protocol answer.** `TxtRecordLookup::lookup_txt` returned `Vec<String>` and spelled "nothing is published at this name" as "the vec happens to be empty" — a distinction §8.4.6 makes normative (absence ADVANCES the mechanism sequence, failure STOPS it) carried by nothing but a doc comment. That is the weakest way to state a rule, and while it was stated that way implementations of this protocol got the absence/failure distinction backwards repeatedly, in both directions — including the shipped port doc itself, corrected in the 2026-08-14e revision below. It is now a type. Landed at alpha, one day after first publication and with no known external implementor, because the alternative is inheriting the convention forever.

- **New `aph_core::discovery::DiscoveryOutcome<T>`** — `Found(T)` or `Absent`. Failure is deliberately NOT a variant: it stays in the `Err` arm of the enclosing `Result` because it carries the §11 code the caller acts on (`APH_E008` unreachable, `APH_E003` outside the validity window, `APH_E014` terminal absence), and because `?` then propagates a failure past every intermediate hop with nobody writing the propagation. The no-downgrade rule becomes something the compiler enforces rather than a discipline each call site remembers.
- **BREAKING — `TxtRecordLookup::lookup_txt` now returns `Result<DiscoveryOutcome<Vec<String>>, AphError>`.** An adapter that answered `Ok(vec![])` for NXDOMAIN answers `Ok(DiscoveryOutcome::Absent)`; one that answered `Ok(records)` answers `Ok(DiscoveryOutcome::Found(records))`. Nothing else about the port moved.
- **BREAKING — `discovery::dns_txt::select_key` returns `Result<DiscoveryOutcome<NotaryPublicKey>, AphError>`** in place of `Result<Option<NotaryPublicKey>, AphError>`. `Option` carried the distinction structurally but did not NAME it, and a mechanism chain that changes vocabulary halfway is how one half comes to mean something the other half does not.
- **The two body-fetch ports keep their `String` return, and that asymmetry is now the contract.** `DidDocumentFetch` and `StatusCredentialFetch` have no served-absence form in v0.1 and do not get one: on the §6.3.3 status path, an `Absent` an adapter could produce from a 404 is exactly the check-skip §6.3.3.4 case 2 exists to deny, and on both paths it would make the response status readable by whoever chose the DID — the disclosure the opaque-error control forbids. Absence at the `did:web` mechanism is decided after parsing, by the document publishing no key under the named fragment (`APH_E014`), which is a statement the document itself made rather than one inferred from a status code. A shape test now fails if either port gains the variant.
- **NO SEMANTICS MOVED, and the inputs were walked one by one to prove it.** NXDOMAIN and NOERROR-with-no-records still advance; timeout, SERVFAIL, REFUSED and every unrecognised resolver error kind still refuse with `APH_E008`; a published-and-expired TXT key still refuses with `APH_E003` and still never reaches the `did:web` fetch; a pinned mechanism with nothing published is still terminal `APH_E014`; every non-success HTTP status on both fetch ports, 404 included, is still `APH_E008`. A new composer test drives all three DNS answers side by side and asserts that an adapter still answering with an empty record set behaves identically to one answering `Absent`.
- **One translation point each side of the port.** `aph-resolver`'s DNS adapter grew a pure `LookupOutcome` → port-answer function so the mapping is testable with no network, and `aph-core`'s composer grew a single DNS-TXT step shared by the terminal and non-terminal callers, which previously held two copies of the query-then-select sequence. `aph-resolver` keeps its own `LookupOutcome` classifier rather than reusing `DiscoveryOutcome`: it classifies an ERROR, so it can never be `Found`, and giving a two-valued classifier a third variant it cannot produce is the kind of type that lies.
- The doc comments that carried the rule shrank to naming the type, keeping only what a signature cannot state: WHY absence advances at all, and which DNS answer falls on which side — the one judgement only an adapter can make.

### Added (revision 2026-08-16b — the operator runbook: surviving key loss, and making the publication deadline visible)

**Two risks the protocol creates for the party running it, neither of which had a written answer.** A notary's identity signs envelopes, publishes discovery AND issues revocation from a single key, so losing that key needs a rotation the lost key cannot authorize. And §6.3.3.3's freshness bound is correct in direction but silent in arrival: a publisher that quietly stops works, and works, and then every verifier in the world refuses at once. Both answers had to fit the constraint the protocol exists for — **the human's authority is the root, the keys stay on the operator's own machine, and no third party is required for the protocol to work** — so every option that would hand custody to a custodian, or insert a service the protocol then depends on, is named and declined rather than left out.

- **New `spec/operations.md`, a NON-NORMATIVE operator runbook in seven sections**: what an operator holds (§1), what losing the signing key costs and does not cost (§2), pre-authorized rotation with four numbered runbooks (§3), the threshold split (§4), publication cadence (§5), the unregistered identifiers an adopter inherits (§6), and a pre-flight checklist (§7). Where it and `spec/aph-0.1.md` disagree the specification wins and the runbook is the defect — stated in the first paragraph of the file, so no procedure below it can quietly outrank the spec.
- **Pre-authorized rotation is §8.4.7's overlap window used defensively, and it needs NO new cryptography.** Generate a successor keypair now on media separate from the signing host, publish its PUBLIC half continuously alongside the primary's under a distinct `kid`, and keep signing with the primary. Because verifiers already resolve and accept the successor, recovery becomes a change to what the operator SIGNS with rather than a change to what the world can READ: no document to edit, no DNS change to propagate, no cache to wait out, and nothing that has to be done with the key that is gone. The phrase "pre-signed by the current key" is deliberately NOT used — v0.1 defines no signed rotation statement and neither publication surface is key-authenticated, so the successor is pre-*authorized* by having been published under the operator's domain control, which is the same authority that publishes every APH key. A signed rotation attestation is a reasonable v0.2 question and is not assumed here.
- **The precondition that makes the mechanism safe is now written as a precondition, not as motivation.** With two keys published and a `proof.verificationMethod` carrying no `#kid` fragment, the two discovery mechanisms fail in two DIFFERENT ways and neither is acceptable: `did:web` resolution refuses outright with `APH_E014`, because `DidDocument::resolve_key` declines to guess among several keys rather than letting document order decide; while `dns_txt::select_key`, given no `kid` to filter on, returns the FIRST record valid at that instant in whatever order the resolver answered, so roughly half of answers resolve the SUCCESSOR's public key against a primary-signed envelope. Both fail closed and no wrong key is ever accepted, but it is a verification outage caused by the continuity mechanism itself, and the DNS half is intermittent per record ordering, which is the expensive kind to diagnose. §8.4.7 bounds this ambiguity to a 30-day overlap window; a permanently published successor makes it permanent. Runbook A therefore verifies the signer emits the fragment BEFORE any second key is published anywhere, the §7 checklist carries it, and §3.3 lists it as a cost of the mechanism. The runbook also states that both keys resolving is NOT the check — two keys resolve perfectly well in exactly the broken state.
- **The threshold split is documented, priced, and deliberately NOT implemented.** An operator MAY split the signing seed *k*-of-*n* using an audited external tool of their own choosing while holding every share themselves. It buys what rotation cannot: no single medium reconstructs the key, loss of up to *n − k* shares is survivable, and because the SAME key is restored nothing published changes and no verifier re-pins. This repository ships no secret-sharing code and does not add any — a subtly wrong sharing scheme does not fail loudly, it leaks the key to anyone holding fewer than *k* shares and the operator finds out never. Choosing an audited implementation belongs to the operator's own threat model; publishing an unaudited one inside a protocol library would make that decision for them, badly. **The decision to escrow at all, and in what form, is the operator's: the runbook presents both options as available, neither as required, and states what each costs.**
- **The largest mitigation in the document is not cryptographic at all.** If the registrar account and DNS credentials live in the same store as the signing key, losing that store loses both and the identity is genuinely unrecoverable — no escrow scheme fixes it, because the missing capability is the ability to PUBLISH. Domain control, not the signing key, is the root of the publication surface's authority: §8.4.4's trust model is the TLS certificate chain and §8.4.5's is the DNS resolution chain, and neither is authenticated by the notary's signing key. Keeping the two recoverable independently — and TESTING the separation rather than believing it — precedes every other procedure in the runbook.
- **Two new PUBLIC methods on `aph_core::credential_status::StatusListCredential`**, purely additive to a crate published at `0.1.0-alpha.1` with no existing signature moved: `seconds_until_republish_due(now) -> Result<i64, AphError>` and `seconds_until_stale(now) -> Result<i64, AphError>`. They report as DISTANCES the two lines `check_freshness` collapses into a verdict — the 120-second republish alarm the publisher owes, and the 360-second refusal cliff (300s bound plus 60s skew) every verifier enforces — whose 240-second gap is the entire warning window. Both are pure functions of the parsed document and the instant passed in; `aph-core` still reads no clock of its own. Both go NEGATIVE rather than erroring once the line is behind you, because a monitor needs "how late am I", not only "too late". Timestamp failures surface `APH_E008` on the same inputs and for the same reason `check_freshness` refuses: a distance must never be rendered as time remaining when the clock could not be read.
- **`spec/security-considerations.md` gains four sections.** §3.6 **loss** of the signing key, held distinct from §3.1's **compromise** — a key nobody has, for which APH offers no protocol-level recovery, because adding one would mean a custodian and that is precisely the dependency the trust model exists to avoid. §3.7 denial of service against a publication surface, where the exposure is deliberate: §6.3.3.4 refuses to let an attacker who can make the status check FAIL thereby choose that it is SKIPPED, so availability is traded for the guarantee that a revoked mandate cannot be laundered back into acceptance — which makes publication liveness a security property rather than an uptime one, silent until it is total. §5.1 pre-authorized rotation and §5.2 the threshold split, both under key-management guidance, because storing a key well is not the same as surviving its loss.
- **README gains a language-agnostic entry point, an operator entry point, and the registration risk where an ADOPTER reads it.** *"Implementing APH in another language"* names four runnable targets in order — parser at `examples/*.json`, verifier at `examples/principal_signed_envelope.json` and its four real Ed25519 signatures over the RFC 8032 §7.1 TEST 2 and TEST 3 PUBLIC test seeds, producer piped through this repo's parser, revocation code at `spec/schemas/` — then states six things the vectors do NOT cover, in full, because overclaiming coverage is worse than admitting a gap. *"Running a notary"* points at the runbook. The Status section now tells an adopter, rather than only §13's IANA text, that `aph://` and `_aph._notary.<domain>` are conventions and not registrations, that neither affects whether an envelope verifies, and that what is genuinely at risk is name ownership.
- **`skills/spec/SKILL.md` gains the runbook**: a repo-map row marking it non-normative, an *Operating a notary* section carrying key loss, pre-authorized rotation and the two cadence deadlines, the unregistered-conventions guidance, and the implement-in-another-language walkthrough.
- **Two coverage claims corrected, on BOTH surfaces that carry them, in one move.** README and the SKILL each said the §8.4.4 DID Document and the two §8.4.5 TXT records are reproduced "byte-for-byte" by the reference tests. Only the TXT half is: `dns_txt`'s tests reassemble both printed tag-lists byte-identically, while `did_document`'s `SPEC_EXAMPLE` is verbatim in CONTENT but re-indented — two spaces in the spec, four in the Rust literal holding it. JSON whitespace is not semantic, so the vector is no weaker; the claim was, and it sat three lines above a heading saying overclaiming coverage is worse than admitting a gap. Separately, the SKILL said the runbook "tabulates all six" unregistered identifiers while its own opening sentence said four exist: §6 **enumerates six and tabulates four**, the two inert ones (the `aph+jws` JWS `typ` and the `urn:aph:schema:0.1:*` `$id`s) being named in prose beneath the table with no cost cell. Both surfaces now read "six in total, four with a cost", matching the runbook's own wording, and the SKILL says explicitly not to quote §6 as a six-row table.

### Added (revision 2026-08-16c — the multi-party exchange: the first tests in this repository where two parties exchange anything)

**Every test here used to be one party validating fixtures.** That is enough to prove a parser and a signature check, and it cannot prove interop — the thing that actually matters is whether a verifier who holds none of the issuer's secrets, and learns about the issuer only from what the issuer published, reaches the right verdict. Until now "conformant" was self-assessed against artifacts produced by the same code doing the assessing.

- **A cast with real separation.** Three parties (Alice, Bob, Carol), each with its own principal key, own notary key, own `did:web` notary origin, own agent DID and own status-list index, plus a seventh identity belonging to no party. A `Wire` models the public internet as two maps of TEXT — DNS TXT names and HTTPS URLs — and each party reads it through its own resolver implementing all three discovery ports. An envelope reaches a recipient only as a JSON string it re-parses. Nothing structural crosses a party boundary, so a test cannot pass because two "different" parties shared a Rust value. Every seed is a single byte repeated 32 times and a tripwire asserts it, so real key material substituted here fails immediately rather than quietly becoming load-bearing in a public repository.
- **Two parties, one admit and four refusals (8 tests).** Bob's verifier resolves a stranger's key through the §8.4.6 chain and admits. Then each refusal proves a DIFFERENT layer and asserts the CODE, not merely that something failed: a foreign key published at Alice's own DNS name resolves successfully and is refused by the signature check (`APH_E001`); the identical bytes admitted earlier are refused when only the evaluation instant moves (`APH_E003`); a re-issued status list with the bit set refuses (`APH_E015`); three covered fields edited in flight refuse (`APH_E011`). A suite that only admits would pass against a verifier that admits unconditionally, which is why the refusals carry the weight. A separate test proves a broken DNS anchor never downgrades to the web origin — and asserts the document was never fetched.
- **Three parties (4 tests).** Alice → Bob → Carol, with Bob both verifying inbound and issuing outbound. Carol's resolver is asked for exactly Bob's three surfaces and nothing of Alice's; Bob's admission of Alice is byte-identical on a wire where Bob himself has published nothing, so a verifier's own identity provably does not enter what it admits; and Carol's verdict on Bob is shown independent of Bob's verdict on Alice in BOTH directions. Forwarding a credential does not launder it into the forwarder's own.
- **Cross-notary revocation (7 tests).** Alice's notary revokes and Bob refuses by reading Alice's PUBLISHED list — the transport proven across a trust boundary rather than inside one process. A forged list is rejected even when it is served from Alice's own origin, names Alice as issuer, and is signed by a real, published, resolvable notary that is simply not Alice. Replaying Alice's own older list cannot roll a revocation back; a status URL on another notary's origin is refused WITHOUT a fetch; an envelope offering no status claim is skipped rather than assumed live. The bit index is chosen so an LSB-first bit-order reversal fails rather than coincidentally passing.

### Added (revision 2026-08-17 — the viability wave: verify arms, four new vectors, a second implementation, a Python binding, the IANA requests, and the rotation draft)

One commit, six deliverables, all aimed at the same target: the distance between "implementable by a stranger" and "implemented twice, checkable end to end".

- **The reference can now VERIFY every suite it requires (and that was not true before).** §8.1 named two algorithms and §8.2 two carriages; the reference implemented one combination and — worse than publishing no vector — REFUSED the others at the envelope layer. The `ecdsa-jcs-2019` verify arm (P-256 issuer, P1363 `proofValue` per the W3C suite definition) and the `JsonWebSignature2020` envelope dispatch onto the existing detached-JWS helper now exist, with ES256 sign siblings mirroring the Ed25519 seam. Additive only; zero new cryptographic primitives; the test that used to pin the refusal now pins the acceptance, and says why the old pin is discharged.
- **`examples/es256_signed_envelope.json` and `examples/detached_jws_envelope.json`** — signed vectors for both previously vectorless MUST-support paths, minted through the reference's own signing seam from PUBLISHED test scalars (RFC 6979 A.2.5, RFC 7515 A.3.1), byte-identity-pinned, and round-tripped through the NEW verify arms in the same tests. ES256 bytes are comparable at all because RFC 6979 makes ECDSA deterministic — stated in the docs, since an implementer who does not know that will assume byte comparison is a bug.
- **The body-hash binding gets its vector, refusal included.** `examples/principal_signed_body.txt` is now the signed golden's published body: `bodySha256`/`bodySize` are the SHA-256 and exact byte length of that committed file, all four signatures regenerated over the real pair, and a new conformance test re-hashes the file recipient-style — plus proves a one-byte-different body refuses with `APH_E009` specifically. §8.3 step 8 was the one verification step exercised by nothing; a positive-only vector would still prove nothing (a recipient that skips the step passes it), so the refusal is the test.
- **A second implementation: APH in TypeScript (`interpreters/typescript/`), full mint AND verify.** Its own RFC 8785 canonicalization, strict parse, proof-structure/mode gates, window and body-hash checks, and §7.2.1 minting order — every signature through the runtime's WebCrypto, zero crypto of its own, zero runtime dependencies, and no Rust consulted beyond the published artifacts. Cross-verification runs BOTH directions as committed bytes: the TS side admits the Rust-minted goldens and refuses the tampered/downgraded/forged-label cases with the right codes, and the TS side deterministically mints `examples/ts_minted_envelope.json` (Ed25519 — WebCrypto ECDSA is randomized, so the ES256 path is covered in the verify direction plus a runtime self-test, stated rather than hidden) which a Rust conformance test verifies in full. Honest scope on every surface: independence of CODE, not of TEAM — the invitation to strangers stands, and their first day is now a diff against two implementations instead of one.
- **`aph-py` (`interpreters/rust/aph-py`)** — a pyo3/abi3 Python binding of the reference, module `aph`, at deliberate EXPORT PARITY with `aph-ts`: the same four envelope-facing operations, the same error identity (one exception type carrying the APH code string a caller can match exactly), and the same JSON-text-in-both-directions FFI rule for the same reason — the untagged proof union is position-sensitive, and a host-language object round trip would let a second deserializer decide which arm parses. Outside `default-members` like its sibling, so the protocol crates never require a Python toolchain.
- **`spec/registrations/` — the two IANA requests §13 promised, written and not submitted.** A complete RFC 7595 provisional registration request for the `aph` scheme and the RFC 8552 underscored-name entry for `_notary` (the registry admits only the label closest to the root; `_aph` arrives derivatively and `_aph._notary` is not an entry in any form — the request says so instead of over-asking). Every contact field is an explicit operator-fills placeholder. §13 flips deferred → drafted, never deferred → done: a draft is not a registration, both names remain unowned, and the collision exposure is unchanged until a human submits and IANA acts.
- **`spec/rotation-attestation-v02-draft.md`** — the NON-NORMATIVE design draft for the v0.2 signed rotation statement, answering what it adds (an attacker who controls the publication surface but NOT the current key can no longer introduce a successor: the bar rises from domain-OR-key to domain-AND-key), what it cannot add (a stolen current key signs a rotation as readily as the operator; the §3.1 bound is the backstop), retraction, and genesis — bootstrap stays domain-anchored; the attestation upgrades CONTINUITY, not GENESIS. The operator-constraint preamble is carried verbatim; nothing normative moved, and all three surfaces that ask the "v0.2 question" now point at the same draft.

### Added (revision 2026-08-17b — the third binding and the second engine)

- `interpreters/elixir/` — **`aph-ex`**, a third binding of the reference implementation: a mix application `aph` over a rustler NIF at `native/aph_nif` with a path dependency on `aph-core`. Public module `APH` exposes the same four envelope-facing operations as the wasm and Python bindings in BEAM idiom — `{:ok, result} | {:error, code}` with the `APH_E*` code travelling as the wire string, so a caller matches `APH_E013` exactly as a TypeScript caller matches it. Zero cryptography on the Elixir side by rule; every signature-touching operation crosses into `aph-core`.
- Envelopes cross the NIF as **JSON text in both directions**, the same rule the other two bindings enforce — restated rather than reused, because the BEAM inverts one premise: Erlang integers are arbitrary precision, so the number-widening hazard does not apply, and what remains is the map/list encoder, which would have to pick an arm of the untagged `proof` union with no schema to consult.
- ⛔ **Every NIF function is decode-string → call-core → encode-result and nothing else**, as a testability rule: a rustler NIF is Rust embedded *in* the BEAM (the inverse of the pyo3 binding), so no `cargo test` can ever reach the term boundary and `mix test` is the only gate that does. A wrapper that grows a branch, a default, or a coercion is a defect *because* cargo cannot reach it. The crate is excluded from the cargo workspace outright — mix drives NIF builds, and two build drivers on one member disagree about target directory, profile, and features — with the exclusion enforced in three layers so relocation cannot quietly undo it.
- One toolchain lesson paid for and pinned: rustler `0.30.0` declares a floating `rustler_sys` requirement, and `rustler_sys 2.3.2` changed a generated FFI signature out from under it, so the pinned release no longer compiled on its own. `rustler_sys = "=2.3.1"` is pinned beneath it with the reason in the manifest — a floating minor under a pinned major is how a build that compiled yesterday stops compiling with no local change.
- The export-parity contract is now **three-way**, stated in all three bindings: an addition to any one is unfinished until it lands in the other two. None of the three is a second implementation; that question remains answered only by `interpreters/typescript/`.
- The TypeScript implementation's crypto-free core now runs under a SECOND ECMAScript engine from cargo. `interpreters/rust/aph-js-harness` loads the compiled output into Boa — an ECMAScript engine written independently in Rust — and drives it from the same expectation table the Node suite reads: one table, two engines. RFC 8785 §3.2.2.3 defers number serialization to ECMAScript `Number::toString`, so the canonical bytes a signature covers are decided by the host float formatter, and a suite that exercises one engine cannot distinguish a correct canonicalizer from one that inherited a host assumption. The cross-engine set covers every JCS vector plus the float-formatting edges (integer-valued doubles, both zeroes, both exponent boundaries, the 2^53 neighbourhood), the published example corpus, and the error taxonomy. A row that disagrees between engines fails with BOTH outputs printed, as a conformance finding about the TypeScript rather than an engine branch. Scope excludes cryptography — a language engine has no WebCrypto — so the four crypto-touching modules are never loaded, and a Rust-backed SubtleCrypto shim is named as future work. The crate sits outside `default-members`, and its tests fail with a BUILD FIRST message when the compiled output is absent.

### Added (revision 2026-08-17c — the fourth binding: Go, over WebAssembly, with a verified artifact)

- `interpreters/go/` — **`aph-go`**, a pure-Go binding of the reference implementation. The reference crate compiles to a plain WebAssembly module (`interpreters/rust/aph-wasm-abi`, a documented ptr/len UTF-8 ABI — deliberately NOT wasm-bindgen, whose exports need JS glue) and runs in-process under wazero, a dependency-free pure-Go runtime. `go get` needs no cgo, no C toolchain, and one artifact serves every platform. Operations are methods on a `*Runtime` handle (`New`/`Close`) — the one idiom divergence in the binding family, justified because the wasm instance has a lifecycle the other three runtimes manage implicitly. Errors carry the APH code as a matchable string via a typed error.
- ⛔ The JSON-text boundary rule applies in Go with its ORIGINAL rationale, not an inherited one: `encoding/json` widens numbers to float64 — the exact hazard that motivated the rule for JS, which vanished on the BEAM's arbitrary-precision integers and returns here. The 2^53+1 tripwire test is back in its original meaning: the integer survives the boundary byte-exact BECAUSE it crosses as text and is never decoded into a Go number.
- **The committed `internal/wasm/aph.wasm` is this repository's one deliberate binary, and it is VERIFIED rather than trusted.** CI rebuilds the shim from a PINNED compiler (a floating `stable` would fail the diff on every rustc release with no repo change) with canonicalized source paths — rustc embeds panic-location and registry paths, which both break cross-machine byte-identity and would leak developer paths into a committed file; the first build did exactly that and the name-hygiene discipline caught it — then byte-diffs the result against the committed copy. A mismatch fails the push. The regeneration recipe lives in the Go README, and the artifact moves in the same commit as any toolchain-pin move.
- The export-parity contract is now **FOUR-way** (wasm/JS, Python, Elixir, Go), flipped on every surface that stated three. None of the four is a second implementation; that remains `interpreters/typescript/` alone.
- Go suite over the published corpus: the signed golden admitted by every operation, forged label refused `APH_E013` and downgrade `APH_E012` by exact code, both proof-union arms round-tripped value-lossless, the widening tripwire, and a string-in/string-out pin. A missing embedded artifact fails with a REGENERATE-FIRST message, never a runtime panic.

### Changed (revision 2026-08-17d — one meaning, one place: the mode spellings)

- `AttestationMode` gains a `FromStr` — the inverse of its existing `label()` and now the ONE place the wire spellings `PrincipalSigned`/`NotaryAttested` are matched. All four bindings' `require_attestation_mode` shims previously carried an identical private copy of that match: four statements of one meaning, each a site where a defaulting typo would BE the mode downgrade that gate exists to refuse. Each shim now delegates (`required.parse()?`), the error message is byte-identical to what every binding produced before, and the shims are thinner — which is the direction glue is supposed to move. ### Changed (revision 2026-08-23 — the first implementer field report, adjudicated: five gaps, six fixes, one new error code)

**The first production consumer outside this repository's own test suites filed a five-item gap report from implementing two channels, with a self-correction worth more than most findings.** Every item was verified against the spec text before ruling; three were real defects, one was a real gap whose answer the protocol's own design principles dictate, one was half-answered by a field the reporter had not met. Their self-correction is now doctrine in the text: *the truth an envelope carries is structural before it is textual* — possession of a well-formed envelope IS the claim that `Approved` was reached, whatever any field says.

- **The mode-vs-verdict confusion gets its sentence, at all three sites that invite it.** `policyDecision` (mandate), `policy.decision` (envelope), and the glossary's "Notary Decision" all name a standing MODE while sounding like a per-act verdict — and the reporter shipped the predicted bug *while reading the spec*. Each site now states: this field records the human's standing configuration, NOT the outcome of this act; the outcome is carried by the state the artifact was issued from. The rename (`policyMode`) was declined — it breaks every published vector to fix what one sentence fixes free.
- **`delegationMandateId`'s null case becomes normative.** A human-not-present envelope (§9.2) MUST carry a non-null `delegationMandateId` — that flow is gated on a mandate, so there is always one to name — and a verifier MUST therefore read null/absent as the human-present flow: *a human personally approved this specific act.* Before this, absence was ambiguous between "one-shot approval" and "standing authority, not recorded," which erased the exact distinction the protocol exists to carry. No wire change; every published vector already conforms (enumerated: the ten null-mandate fixtures all truthfully claim human-present; both mandate-carrying fixtures name theirs).
- **`APH_E016 MandateRequired` — the taxonomy grows to sixteen.** Unrooted authority: a §9.2 act with no matching unexpired Delegation Mandate. The reporter had to misuse an invalid-mandate code for this case, which conflates absence with failure — the distinction this specification makes structural everywhere else (§8.4.6). The completed family: `APH_E007` nobody was asked · `APH_E016` nothing authorized this · `APH_E011` the authorization is invalid · `APH_E003` it expired · `APH_E015` it was withdrawn. Both implementations carry the new code; every "fifteen" was found by sweep and flipped — including a count-named Rust test whose hand-maintained census had silently missed the new variant, the second time that exact list failed the way its own comment warns.
- **`PendingDecision` produces NO wire artifact, normatively** — and `APH_E007`'s remedy no longer names a "Deferred-for-Review queue" the spec never defined. A held request has no mandate, no envelope, no APH representation; holds are implementation-local. Stated rather than left silent because the pressure is real: signing something is easier than representing "held," and an artifact minted from a hold would assert, by existing, an approval that has not happened.
- **The mandate's `contentClass` closes (erratum).** The §6.2 table read "…`Channel`, etc." — a required, SIGNED field left open, while the envelope's §7.1.6 closed the same vocabulary. Two conformant notaries could have emitted values the other rejects, and neither would have been wrong. Closed by reference to §7.1.6, with the erratum dated in the row, per the `google_chat` precedent.
- **`actChain` element order is declared (found during adjudication, not filed by the reporter):** root delegate first, most recent actor last, the human never an element. The array is inside the signed bytes and RFC 8693's nested claim flattens either way — two producers choosing opposite orders would sign different bytes for the same chain. Declared while exactly one producer exists and every published vector carries the empty array, which is the last moment this rule is free.

### Changed (revision 2026-08-28 — the axis rule: §7.1.5's `kind` names a medium, and where to ask for a new one)

- **§7.1.5 now states the axis `kind` measures, because three independent implementations hit the same wall on the same day.** All three reported a shipping value that §7.1.5 does not define, surfaced when the reference implementation made the closed vocabularies into field types and an unrecognized value stopped round-tripping in silence. The value turned out not to be a missing channel at all: it named an INTERNAL PERMISSION SCOPE in the emitting system, placed in a field that means end-delivery medium — two axes wearing one string, which is why that system's own mandate check had been refusing its own peers. §7.1.5 now says what `kind` measures and what it does not (not the emitting subsystem, not the agent-to-agent rail per §1.1.1, not an authorizing scope), and states the consequence the closure already implied: where a sender's routing concept has no entry, the correct value is the kind naming the medium it ultimately delivers on.
- **§7.1.5 now says where to ask for a new value**, which is the half this project got wrong. A closed vocabulary that does not say how to extend it invites coinage from anyone who needs a word it lacks, and coinage in a signed field is permanent. The pointer to `rfcs/README.md` is the remedy; the finding is recorded against this project rather than its implementers.
- **`rfcs/0004-vendor-extension-channel-kind.md` (RFC 0004) records the rejection of an open vendor arm**, permanently rather than "not yet": `Other(String)` in a closed set is a repeal of the closure and not an extension of the set, since it restores the any-string-round-trips behaviour the closure removed and lets a producer disable a recipient's check by writing a word that recipient has never seen — the same reasoning §6.3.3 already gives for `statusPurpose`. The RFC is equally explicit that a NAMED first-party variant is categorically admissible (six of seven kinds are vendor names), that it must go through the ordinary process, and that a request from this project gets more scrutiny than an outside one rather than less.
- **The specification is now a POPULATOR of the closed vocabularies rather than prose beside them.** Three artifacts declare the same two closed sets — the spec, the Rust reference types, and the N Lang Snapp bundle — and only the second and third were welded together. The spec's enum tables were checked by nothing, in either direction: a widening that moved the type but not the table publishes a kind no implementer can learn about, and one that moved the table but not the type publishes a kind the reference refuses. Both reach us as the same field report. All FOUR restatements are now checked (§7.1.5 and §7.1.6 define; §6.2 restates both for the mandate), because the §6.2 content-class row already carries an erratum recording that exactly this drift happened once before. Verified by mutation rather than by observing green.
- **Recorded in RFC 0004: the axis rule is not mechanically enforceable, and nothing checks it.** The closed type refuses an unrecognized STRING — the case that actually occurred. It cannot catch the same error committed with a RECOGNIZED one: a sender that coined `email` to name an internal scope parses cleanly, satisfies every check in §8.3, and binds nothing. The axis is a claim about what the sender meant, and no verifier can check intent. A reader who finds the rule in the specification is entitled to know whether anything enforces it; nothing does, and the RFC now says so.
- Nothing normative moved: no kind added, renamed, or removed, and no envelope's validity changes. §7.1.5 and Appendix A stand as written.

### Changed (revision 2026-08-28b — the consent question RFC 0004 appeared to foreclose, answered on its own terms)

- **RFC 0004's `email` mapping is corrected to say what it actually settles.** It stated the mapping flatly, which read as disposing of every question about mail-shaped channels. It does not. A separate request was already open when it was written — argued on CONSENT GRANULARITY rather than vocabulary — and RFC 0004 neither engaged nor answered it while appearing to close it. A scope name in a medium field is an error; asking whether one medium serves two materially different recipients is a design question with a real answer on either side, and conflating the two would have retired a live request by accident.
- **`rfcs/0005-recipient-class.md` (RFC 0005, Draft) takes up the real problem.** A human granting `allowedChannels: ["email"]` means *my agent may send email for me*; that same grant now also authorizes unattended inter-organization machine-to-machine mail, at machine rate, while she sleeps. Nothing keyed on `kind` can separate them, because at the level `kind` operates they are the same event — the bytes land in a real mailbox at a real MX either way. The mandate is where a human's authority is written down, and it cannot currently express a distinction the human plainly intends.
- **The proposed eighth kind is refused, and the generalization test is why.** If recipient class belongs in `kind`, then `a2a_slack`, `a2a_discord`, `a2a_teams` and the rest all follow, because an agent can be the consumer on any medium: the set does not grow by one, it DOUBLES, and doubles again for the next refinement anyone proposes. A refinement that must be applied to every member of a set is not a member of that set — it is a second dimension wearing a member's clothes. RFC 0005 proposes it as an orthogonal value that composes with all seven kinds instead.
- Recorded in RFC 0005's security section rather than left implicit: a recipient class asserted by a sender is a CLAIM, not a proof. It constrains an honest-but-over-broad agent — which is the actual threat, a human's own agent doing more than she meant — and does not constrain a hostile one. Any concrete proposal must say so plainly rather than describe it as a control it is not.
- Nothing normative moved. RFC 0005 proposes a shape and names the questions that must be settled before any field exists, including the rollout rule: §7.1.5's vocabularies are closed and now typed, so an older verifier meeting an unknown value fails at strict parse BEFORE the protocol's own error vocabulary is reachable — without a version-gated emission rule, adding any new closed-vocabulary value is a flag day for every deployed verifier.
